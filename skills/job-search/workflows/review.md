# Review responses and improve the search

Use for “what next?”, application status, inbox triage, funnel review or learning
from outcomes. This stage can recommend another workflow without executing it.

## Read the relevant state

Use [shared sources](../references/shared-state.md) and the focused
[status checks](../references/status.md). Read only what the request needs:
an interview debrief does not require scanning every GitHub commit or mailbox.
For a general status check, reconcile application history, open blockers,
interview dates and resume integrity before recommending a next action.

Keep missing data distinct from zero activity. Read the tracker schema actually
present, preserve normalized application URLs, and account for older archive
layouts. Do not change records solely to make ledger/tracker/Vault totals agree.

## Inbox evidence

Prefer the existing [Gmail worker](../../gmail-ai-daily-ops/SKILL.md) and its
small read operations. Check the mailbox/profile first: job search uses
`yplmicro@gmail.com`. A generic connector is a fallback only after its profile
is verified as that account. Wrong-account or unavailable access is reported,
not replaced with another mailbox or an invented unread count.

Read the relevant thread and identify employer, role, message date and the
specific signal. Match requisition identity when present; company name alone
is ambiguous when several applications are open. Cite the source message or
thread for proposed status changes.

- An acknowledgement confirms receipt; it is not an interview invitation.
- An assessment, recruiter screen and later interview round are different next
  steps. Preserve the evidence and the existing tracker's vocabulary.
- A rejection can close only the application it actually identifies.
- An offer does not establish acceptance, hiring or a declined offer.
- Silence is an observation, not proof of rejection or a withdrawal decision.

A status-only request produces proposals and never changes records. Write a
tracker update only when the current request explicitly asks to update or
reconcile records, or explicitly confirms the proposed changes. Use the existing
schema and resolve ambiguous matches or conflicting signals before any write.
The status reference applies to the read-only part of this workflow. Do not send replies,
follow-ups or referral messages from this workflow. Draft requested text for
review, leaving final sending to an explicitly authorized action.

## Feedback into the lifecycle

Compare like-for-like cohorts where records support it: verified submissions,
acknowledgements, interviews and outcomes by role family, source and resume
version. Report the denominator and observation window. Small samples and
recent applications support a tentative hypothesis, not a confident verdict
on the resume or a new universal eligibility threshold.

Use repeated evidence to propose search keywords, source mix, shortlist
priorities, resume evidence to surface, or interview topics to practice.
Keep form failures separate from hiring outcomes. A ManualFinish streak is a
reason to surface the existing unresolved gates, not to automate around them.

## Output and handoff

Lead with the next useful action and any required user decision. Include the
supporting status changes, material data inconsistencies and open human
blockers. Route to search, evaluate, resume, materials, apply or interview as
appropriate; a dashboard recommendation does not authorize that next action.
